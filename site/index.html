seisin

seisin (n.) — the legal possession of a piece of land. Not who owns it on paper: who holds it now.

Give each AI agent its own folders and its own keys.

The kernel enforces it. When it blocks something, seisin tells you whose file it was — which turns a dead end into a handoff.

GitHub npm Read the README

What you see

The kernel says no. seisin says whose.

Other permission layers answer yes or no, and the good ones say which rule it was. Answering “no, and it belongs to backend” is the part an operating system cannot know.

$ seisin run frontend -- sh -c 'echo // fix >> src/api/orders.ts' sh: src/api/orders.ts: Operation not permitted seisin: 1 kernel denial(s) recorded 1 pending request(s) #1 frontend wants write on src/api/** (owned by backend) first asked over src/api/orders.ts seisin grant <n> [--reason "…"] · seisin decline <n> [--reason "…"]

The agent can ask before it reaches, too — seisin whose src/api/orders.ts answers from inside the box.

The loop

Denied → whose → a person decides

Nothing is approved by an agent, and nothing is approved through the MCP server. Granting happens in a terminal or in the console, by a person.

How you use it

Sixty seconds

  1. npm install -g seisinOn Linux, three system packages first — the README lists them.
  2. seisin initProposes a policy from what your repo already says: .claude/agents/, then CODEOWNERS, then a blank start. It proposes — a generated policy you did not read is not a policy.
  3. seisin checkThe map, and every way it does not hold. Read it before you trust it.
  4. seisin wireLets the agent record what it does, so a refusal can be explained afterwards.
  5. seisin run frontend -- claude -p "…"Runs the agent inside its own territory. Anything not listed is denied — there is no permissive default.

The policy

One file, at the root of your repo

[keys]
dir = ".secrets"

[network]
allow = ["github.com", "*.github.com"]

[roles.frontend]
writes = ["src/web/**", "public/**"]
keys   = ["netlify-token.txt"]

[roles.backend]
writes  = ["src/api/**", "migrations/**"]
keys    = ["database-url.txt"]
network = ["api.stripe.com"]
writes
The role’s territory. A path is in exactly one role’s territory, or in several — and overlap is allowed and reported.
keys
What the role may hold. Either a file under the declared key directory, or a scheme:// reference a provider resolves outside the sandbox — the role gets the value, never the file.
network
Per-role, and it replaces the global list rather than adding to it: a domain in [network] is reachable by every role, including the ones whose job is to reach nothing.
HTTP(S) works; SSH does not. The allow list is enforced by proxies the runtime starts. One of them is a SOCKS5 proxy that could carry SSH, but the chain breaks at its last link: it requires authentication and the ProxyCommand the runtime wires up cannot send any. Use an HTTPS remote for git, and run SSH deploys outside the confined turn.

The honest parts

What it is not

  • Not a sandbox. It sits on top of one. The isolation comes from the OS, via @anthropic-ai/sandbox-runtime; what seisin adds is which role a path belongs to, and therefore who to ask next.
  • Not an orchestrator. It does not route work, schedule agents or decide who does what.
  • Not a defence against a hostile agent. Tampering with the log is closed; a hostile agent can still add lines to its own history.
